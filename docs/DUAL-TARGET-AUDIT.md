### Boot writer and revised maintenance design

The user selected VM-first testing plus a preserved known-working boot set and manual recovery instead of automatic one-time trial and promotion. This supersedes those automatic maintenance requirements in the original plan. ARM64 VM results do not establish Surface hardware compatibility. Preserve and verify the prior kernel, initramfs, DTB and recovery files; do not change the active boot selection if staging, space or verification fails. An actual physical update still requires an authorized device and recovery path. The manual restore path and interruption behavior now have host fault-injection coverage; no FAT or hardware power-loss guarantee is asserted.

AMD64 `install-target.sh` saves an Ubuntu GRUB fallback before installing the custom kernel; `kernel-preinst` resets that fallback and `kernel-postinst` requires NVIDIA DKMS and signing before recording a pending kernel. `activate.sh` uses GRUB one-time boot and promotion after runtime checks.

SP12 `install-fallback-target` inspects `/target`, requires a matching packaged DTB for the reference kernel, takes `/run/lock/sp12-boot.lock`, builds an ARM64 removable loader and stages `/sp12` payloads. Before replacement, `sp12-save-recovery` copies a complete prior payload set to `/var/lib/sp12-linux/recovery` in the target's `/var/lib` filesystem and records checksums. `sp12-sync-boot` uses the same lock, checks space, copies changed files to staging and keeps in-process rollback copies; its cleanup attempts restoration and returns the ESP to read-only. `sp12-restore-recovery` verifies the persistent snapshot, restores it to the ESP under the lock, and leaves the backup in place. Their common `/sp12/vmlinuz`, `initrd.img` and `dtb` names represent one active payload. A host fault-injection test interrupts promotion after the first file and restores the complete previous set. The ESP update remains file by file and does not claim atomic replacement or FAT power-loss safety; do not copy AMD64 GRUB state logic into this loader.

The reference `install-fallback-target` enforces packaged-DTB equality only for its exact `7.3.0-sp12-v7.3-platform` release; passing a different release skips that particular check. Its GRUB guard installer also explicitly requires that reference release in `boot.conf`, while `kernel/installer-kernel.py` pins the reference package identity. The new `7.3.1-psycachy-sp121` path must adapt and test all three checks against the authenticated target manifest and matching DTB before use. Calling the reference scripts unchanged with the new name would either bypass an identity check or fail to install the guard.

| --- | --- | --- | --- |
| **Firmware & ESP structure** | Standard UEFI x86_64; `/boot/efi/EFI/ubuntu/` with `grubx64.efi` | Removable UEFI AArch64; `/boot/efi/EFI/BOOT/BOOTAA64.EFI` + `/boot/efi/sp12/` | Distinct paths on ESP; scripts check `$(uname -m)` / `dpkg --print-architecture` before touching ESP layout |
