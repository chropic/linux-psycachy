# SP12 ARM64 package lifecycle check — 2026-11-09

The candidate image and headers packages (`7.3.1-1psycachy1`) were installed
in a disposable ARM64 QEMU guest from a local APT repository with dependency
resolution. The persistent root and ESP backing images were unchanged; this
run used `root4.qcow2` and `esp4.qcow2` copy-on-write overlays. No host package
or physical device was changed.

Before package configuration, the updated target installer was applied to the
mounted guest target through `/mnt/target`; it installed the GRUB helper
diversion, SP12 guard, boot synchronization helper, and hooks. The live image's
`update-initramfs` was a disabled stub, so the disposable guest was directed to
the distribution `update-initramfs.distrib` implementation. This was a guest
only workaround.

## Install and configure

The retry of `dpkg --configure -a` returned 0. `flash-kernel`,
`initramfs-tools`, and both candidate packages reported installed status, and
`dpkg --audit` was empty. The kernel post-install hook initially reported no
previous payload directory; a later trigger preserved the complete payload
set. The initramfs was generated, and `sp12-sync-boot` completed. The initramfs
generator warned that it could not resolve `/dev/root` or identify the overlay
root filesystem in this init=/bin/bash guest; those warnings do not establish
normal boot behavior.

The ESP was mounted read-only after hook completion. Payload hashes matched the
kernel, initrd, and DTB source files at that point:

| `vmlinuz` | 17,170,944 | `91b0e460d80ce5d2929eb078ca3d2c6abf9578cf55064fee4b965dc403158947` |

`SP12BOOT` was present. These hashes verify the ESP payload contents, not a

## Removal attempt

APT removed the candidate image and headers. The image package's removal hook
deleted its root initrd, and flash-kernel reported selecting the remaining
`7.3.0-sp12-v7.3-platform` kernel. The removal command returned 100 when the
pending flash-kernel trigger failed: `dpkg-query: no packages found matching `
followed by a flash-kernel post-install failure. The final package states were
candidate image `rc`, candidate headers `un`, and flash-kernel half-configured;
`dpkg --audit` reported flash-kernel as the only incomplete package.

The ESP remained read-only and retained the same kernel/initrd/DTB bytes after
removal, while the candidate root initrd was absent. Therefore the retained ESP
payload was not evidence of a working fallback. The flash-kernel removal-trigger
failure and fallback behavior need another disposable guest run.

## Removal-trigger diagnosis

A follow-up read-only inspection used nested COW overlays over the preserved
post-removal guest. `flash-kernel` 3.110's `get_kernel_status()` looks up the
owner of each kernel path emitted by `linux-version list --paths`, then asks
`dpkg-query` for that package's status. The selected remaining
`7.3.0-sp12-v7.3-platform` kernel was present under `/boot`, but
`dpkg-query -S /boot/vmlinuz-7.3.0-sp12-v7.3-platform` returned no owner. The
same check for `/usr/lib/modules/7.3.0-sp12-v7.3-platform/vmlinuz` also found
no owner. With an empty package name, the status query produces the blank
`dpkg-query: no packages found matching ` error seen during removal. The
generic `7.3.0-9-generic` kernel path in this fixture was also unowned. Thus the
removal failure is explained by the guest fixture's unmanaged fallback kernel;
it does not demonstrate a failure in the candidate package's removal script.

The symptom also matches a known `flash-kernel` 3.110 issue reported for Linux
7.2+ split kernel packaging, where `vmlinuz` moved under
`/usr/lib/modules/$ver` and ownership changed to `linux-binary-$ver`:
[Debian bug #1148115](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1148115),
[proposed flash-kernel change](https://salsa.debian.org/installer-team/flash-kernel/-/merge_requests/86).
The local fixture's fallback paths had no package owner, so the guest result
does not establish whether the upstream split-kernel issue also affects a
properly package-managed SP12 fallback.

For a conclusive repeat, start from a guest with an installed, package-managed
fallback kernel. Record the kernel package status and ownership of the paths
returned by `linux-version list --paths` before removing the candidate. Then
require clean removal, an empty `dpkg --audit`, restored fallback payloads, and
a fallback boot.

candidate image and headers packages were unpacked and configured again.
`dpkg --configure -a` returned 0, all four relevant packages reported `ii`,
`dpkg --audit` was empty, and the ESP was read-only after the hooks ran. The

the attempt does not establish a normal installed-system reboot. A boot through

## Package-managed fallback removal check — 2026-11-09

A fresh nested-COW guest installed Ubuntu ARM64 kernel packages
`linux-image-7.3.0-9-generic`, `linux-modules-7.3.0-9-generic`, and
`linux-main-modules-zfs-7.3.0-9-generic`, all version `7.3.0-9.9`. The
fallback image package owned `/boot/vmlinuz-7.3.0-9-generic`; the modules
package owned
`/usr/lib/firmware/7.3.0-9-generic/device-tree/qcom/x1p42100-microsoft-sp12in.dtb`.
Its initrd was generated by `initramfs-tools`.

The first repeat still failed because this fixture also contained an unmanaged
`/boot/vmlinuz-7.3.0-sp12-v7.3-platform` path. `flash-kernel` selected that
newer path and failed its blank package-owner lookup even though the generic
fallback was installed. After confirming `dpkg-query -S` returned no owner, the
test removed only that unowned fixture kernel from the disposable COW guest.
The next removal attempt exposed a second issue: the boot-sync hook remained
configured for the candidate after its package was removed. Its initramfs hook
then failed with `missing required source: /boot/vmlinuz-7.3.1-psycachy-sp121`.

The repository now installs a pre-remove hook and
`sp12-select-fallback`. Before the active image is removed, the helper requires
an installed package owner for the fallback kernel and the matching SP12 DTB,
copies that DTB to `/boot`, updates `boot.conf`, and calls the existing
rollback-safe sync helper. If validation or sync fails, the helper restores
the active configuration and aborts removal. Four focused fallback-selection
tests cover selection, rejection of an unowned kernel, sync-failure rollback,
and ignoring package upgrades.

For the final retry, `apt-get remove` returned 0. The candidate image reached
`rc`, the headers package reached `un`, the generic image/modules/ZFS-module
packages remained `ii`, `flash-kernel` and `initramfs-tools` were `ii`, and
`dpkg --audit` was empty. `linux-version list --paths` contained only the
package-owned generic kernel. The pre-remove hook selected
`7.3.0-9-generic`, and the three ESP payloads matched their source files:

| Payload | SHA-256 |
| --- | --- |
| `vmlinuz` | `1bb5529f0cee6ed43702d1d09a92ea850c1b0bbdf4dbdf1ef7dbe4ccaa2270cf` |
| `initrd.img` | `b5b1297c9c92db3e3608af74e628ec6088f9e56a2b74a6a54918ae200cd10afd` |
| `dtb` | `8c3b80a4b2cad15e95286e2d8e8c4b88cc0c0b47cb975b2a94c5d7e3cbcb14ba` |

This verifies package removal and fallback payload selection in the disposable
guest. The guest remained booted from the candidate kernel passed directly to
QEMU; this is not a boot of the fallback from ESP/GRUB. A normal initrd/UEFI
reboot and SP12 hardware boot remain unverified. The successful serial
transcript is retained locally at
`output/phase1-lifecycle-vm/fallback-removal-test3.log` (SHA-256
`5767d3470066175150cbff42af2e3b0071e9ef645a88be835732441cfba3435a`).

## ARM64 UEFI fallback payload smoke check — 2026-11-09

A further disposable QEMU `virt` check used AAVMF 2026.05 with software
emulation. GRUB could not see the ESP's secondary virtio block device, so the
exact fallback kernel and initrd files were copied from a read-only raw
conversion of the ESP into a temporary FAT boot disk. Their hashes matched the
ESP payloads above. A standalone ARM64 GRUB EFI loader on that disk selected
the copied payload using a temporary zero-byte `SP12BOOT` marker, loaded
`7.3.0-9-generic`, and started its initrd under UEFI. The QEMU-generated
`virt` device tree was used; the SP12 DTB was not passed to the generic QEMU
machine.

The kernel reached `/init`, ran the initramfs `casper-premount` hook, and
mounted root UUID `048bbb9c-e82e-42ad-bf34-e5d675e981bb` read-only. The
initramfs then unmounted it and stopped progressing through the copied live
media's Casper path; no systemd target or login was recorded. This is UEFI,
GRUB, kernel, initrd, and root-mount smoke evidence. It is not a normal
installed-system reboot, a boot from the ESP-resident loader, or validation of
the SP12 DTB or Surface hardware.

The serial transcript is retained locally at
`output/phase1-lifecycle-vm/uefi-fallback-tcg/serial.log` (SHA-256
`3edbe369444c2fbac50ed4625b36769668cb784446c3e748c38ebb3ebdd9861a`). The
temporary EFI loader, raw ESP inspection image, extracted payload copies, and
new qcow2 overlays are under the same ignored output directory.
