# SP12 ARM64 package lifecycle check — 2026-11-09

The candidate image and headers packages (`7.3.1-1psycachy1`) were installed
in a disposable ARM64 QEMU guest from a local APT repository with dependency
resolution. The persistent root and ESP backing images were unchanged; this
run used `root4.qcow2` and `esp4.qcow2` copy-on-write overlays. No host package
or physical device was changed.

Before package configuration, the updated target installer was applied to the
mounted guest target through `/mnt/target`; it installed the GRUB helper
diversion, SP12 guard, boot synchronization helper, and hooks. The live image's
`update-initramfs` was a disabled stub, so the disposable guest was directed to
the distribution `update-initramfs.distrib` implementation. This was a guest
only workaround.

## Install and configure

The retry of `dpkg --configure -a` returned 0. `flash-kernel`,
`initramfs-tools`, and both candidate packages reported installed status, and
`dpkg --audit` was empty. The kernel post-install hook initially reported no
previous payload directory; a later trigger preserved the complete payload
set. The initramfs was generated, and `sp12-sync-boot` completed. The initramfs
generator warned that it could not resolve `/dev/root` or identify the overlay
root filesystem in this init=/bin/bash guest; those warnings do not establish
normal boot behavior.

The ESP was mounted read-only after hook completion. Payload hashes matched the
kernel, initrd, and DTB source files at that point:

## Removal attempt

APT removed the candidate image and headers. The image package's removal hook
deleted its root initrd, and flash-kernel reported selecting the remaining
`7.3.0-sp12-v7.3-platform` kernel. The removal command returned 100 when the
pending flash-kernel trigger failed: `dpkg-query: no packages found matching `
followed by a flash-kernel post-install failure. The final package states were
candidate image `rc`, candidate headers `un`, and flash-kernel half-configured;
`dpkg --audit` reported flash-kernel as the only incomplete package.

The ESP remained read-only and retained the same kernel/initrd/DTB bytes after
removal, while the candidate root initrd was absent. Therefore the retained ESP
payload was not evidence of a working fallback. The flash-kernel removal-trigger
failure and fallback behavior need another disposable guest run.

## Removal-trigger diagnosis

A follow-up read-only inspection used nested COW overlays over the preserved
post-removal guest. `flash-kernel` 3.110's `get_kernel_status()` looks up the
owner of each kernel path emitted by `linux-version list --paths`, then asks
`dpkg-query` for that package's status. The selected remaining
`7.3.0-sp12-v7.3-platform` kernel was present under `/boot`, but
`dpkg-query -S /boot/vmlinuz-7.3.0-sp12-v7.3-platform` returned no owner. The
same check for `/usr/lib/modules/7.3.0-sp12-v7.3-platform/vmlinuz` also found
no owner. With an empty package name, the status query produces the blank
`dpkg-query: no packages found matching ` error seen during removal. The
generic `7.3.0-9-generic` kernel path in this fixture was also unowned. Thus the
removal failure is explained by the guest fixture's unmanaged fallback kernel;
it does not demonstrate a failure in the candidate package's removal script.

The symptom also matches a known `flash-kernel` 3.110 issue reported for Linux
7.2+ split kernel packaging, where `vmlinuz` moved under
`/usr/lib/modules/$ver` and ownership changed to `linux-binary-$ver`:
[Debian bug #1148115](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1148115),
[proposed flash-kernel change](https://salsa.debian.org/installer-team/flash-kernel/-/merge_requests/86).
The local fixture's fallback paths had no package owner, so the guest result
does not establish whether the upstream split-kernel issue also affects a
properly package-managed SP12 fallback.

For a conclusive repeat, start from a guest with an installed, package-managed
fallback kernel. Record the kernel package status and ownership of the paths
returned by `linux-version list --paths` before removing the candidate. Then
require clean removal, an empty `dpkg --audit`, restored fallback payloads, and
a fallback boot.

## Candidate boot checks

In a fresh nested COW root based on the retained post-removal image, the
candidate image and headers packages were unpacked and configured again.
`dpkg --configure -a` returned 0, all four relevant packages reported `ii`,
`dpkg --audit` was empty, and the ESP was read-only after the hooks ran. The
kernel and generated initrd matched their copies exported from the guest:

| Payload | Size (bytes) | SHA-256 |
| --- | ---: | --- |
| Package kernel | 17,170,944 | `91b0e460d80ce5d2929eb078ca3d2c6abf9578cf55064fee4b965dc403158947` |
| Generated initrd | 166,614,961 | `e6e2a662dc2716c03a53ed8aae295072c28c198c861c85a50baaaa60db199c94` |

The ESP kernel and initrd hashes matched these source files. A direct QEMU
`virt` boot using the package kernel and the installed guest root reached
`/bin/bash`; `uname -r` reported `7.3.1-psycachy-sp121`, both candidate packages
reported `ii`, and `dpkg --audit` was empty. This checks the installed kernel
against a generic virtual machine; it is not an SP12 hardware or firmware boot.

A second QEMU attempt used the package-generated initrd and requested the
multi-user target. It reached the initramfs and completed
`/scripts/casper-premount`, but no systemd target or login was recorded. This
root image is derived from live media and includes casper initramfs hooks, so
the attempt does not establish a normal installed-system reboot. A boot through
the ESP/GRUB path and a normal reboot remain open.
